CRM SaaS B2B — Roadmap del proyecto

Guía de prioridades y próximos pasos de desarrollo

Proyecto: CRMProject · Fecha: 31 de mayo de 2026 · Stack: Django + DRF

1. Estado actual del proyecto

✓ Completado

  • Modelo User custom (email, roles, auditoría)
  • App users con manager y migraciones
  • Dominio de ventas: Customer, CallLog
  • API REST básica con Django REST Framework
  • Login JWT (LoginUserJWT)
  • Admin parcial configurado

✗ Pendiente / desalineado

  • Vistas de usuario aún buscan username, first_name
  • Serializers desactualizados respecto al nuevo User
  • Endpoints sin protección JWT en la mayoría de rutas

  • Sin permisos por rol (SALES_PERSON, MANAGER, ADMIN)
  • Sin aislamiento de datos entre empresas

2. ¿Por qué no empezar por validaciones?

Las validaciones son importantes, pero en un SaaS B2B tienen sentido cuando ya existe contexto: quién es el usuario, a qué organización pertenece y qué rol tiene.

Sin ese contexto, validarías cosas como:

  • Email único globalmente (incorrecto para B2B — debe ser único por organización)
  • Permisos sin saber si el usuario puede ver ese cliente
  • Reglas de negocio sin aislar datos entre empresas
Conclusión: Las validaciones van en la fase 5, después de auth, multi-tenancy y permisos. Antes de eso, construirías reglas sobre una base incompleta.

Autenticación completa En progreso

Ya tienes login JWT. Falta cerrar el flujo:

POST /api/auth/login/     → JWT (access + refresh)  ✓ hecho
POST /api/auth/refresh/   → renovar token
GET  /api/auth/me/        → perfil del usuario autenticado
Proteger todos los endpoints con IsAuthenticated
3

Multi-tenancy — corazón del B2B SaaS Crítico

Cada empresa cliente (tenant) debe tener sus datos completamente aislados.

class Organization(models.Model):
    name = models.CharField(max_length=150)
    slug = models.SlugField(unique=True)
    is_active = models.BooleanField(default=True)
    created_at = models.DateTimeField(auto_now_add=True)

class User(...):
    organization = models.ForeignKey(Organization, ...)

class CustomerModel(...):
    organization = models.ForeignKey(Organization, ...)

Regla de oro: todo queryset filtra por organization del usuario autenticado.

4

Autorización por rol

Ya tienes el enum Role. Ahora hay que usarlo en permisos DRF:

Rol Permisos
SALES_PERSON Ver y editar solo sus clientes y llamadas
MANAGER Ver clientes y llamadas de todo el equipo / organización
ADMIN Gestionar usuarios de la organización

Implementación: clases como IsOrgMember, IsManagerOrAdmin.

5

Ahora sí: validaciones con org y rol definidos.

Capa Responsabilidad Ejemplo
Serializer Formato, campos requeridos Email válido, teléfono con formato

Servicios Reglas de negocio complejas Email único por org, notas obligatorias si status=connected
